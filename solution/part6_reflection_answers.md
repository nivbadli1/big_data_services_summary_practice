# Part 6 - Reflection: answers

**1. A deleted order.** The DAG asks for `updated_at > watermark`. A deleted document does not exist any more, so there is nothing to match: **the DAG never finds out**. `orders_silver.csv` keeps the old row forever, and `courier_payouts.csv` / `restaurant_fees.csv` keep counting it. Options: soft deletes (`deleted_at` + `updated_at` set, the row is filtered out downstream), a periodic full reconciliation (compare all ids), or CDC, which sees deletes as events (Appendix A).

**2. Two updates between runs.** The 11:00 run sees only the **latest** version (delivered at 10:40). The "accepted at 10:05" state is lost; you only know it existed if the document keeps a history field. For payouts that is fine (only the final state matters). For questions like "how long did restaurants take to accept?", the batch path cannot answer, but the Kafka events (every state change) or CDC can.

**3. Airflow down for 2 days.** `catchup=False`, so Airflow starts **one** run, not 48. That run reads `updated_at > <watermark from 2 days ago>`, so it picks up **everything** that changed in the 2 days. Nothing is lost; the run is just bigger. With `now() - 1 hour` instead of a watermark, that run would read only the last hour and **47 hours would be lost silently**. A watermark is "where I stopped", not "what time it is".

**4. Why `_id = order_id`.** (a) **Duplicates / replays** (chaos `duplicates`, a consumer restart that re-reads uncommitted offsets): the same event overwrites the same doc instead of adding a second one, so counts are not inflated. (b) **One row per order**: the 4-5 lifecycle events of an order collapse into its current state, so "how many orders are late" is a simple count and not a "latest event per order" query. Bonus (c): you can **rebuild** the index from Kafka at any time and get the same result.

**5. Two `is_late`s.** The consumer's is a **live estimate** (open orders can become late later; the flag can be stale, see 5.4). The DAG's is computed from the system of record after the fact, only for delivered orders, with cleaned data. They disagree for open orders, for late-arriving events, and when an event was lost or arrived out of order. For Finance (payouts, bonuses) the **batch** number is the truth. For Ops (act now) the live one is the useful one.

**6. Re-process one day.** With this design: no watermark per day exists, so you would (a) reset `quickbite_watermark` to before 3 Oct and re-run. That re-reads everything after it, which is correct (Silver is an upsert, Gold is fully recomputed from Silver, `daily-summary` uses `_id = date`), just more work. Or (b) fix the mapping and only recompute Gold from Silver. Easier designs: **partition** Silver/Gold by date (`gold/date=2026-10-03/...`), use the DAG's `data_interval_start/end` instead of a free watermark so Airflow's **Clear** / **backfill** can re-run exactly one interval, and keep the raw extracts (Bronze) so re-processing never needs the source again.

**7. pandas -> PySpark.** `flatten_orders` -> `spark.read` (Mongo Spark connector) + `select` with `col("customer.contact.email")`, `coalesce()`, `when()`, `to_timestamp()`; `normalize_city` -> a join with a small mapping DataFrame (or `create_map`); `split_quality` -> `Window.partitionBy("order_id").orderBy(desc("updated_at"))` + `row_number()`, and `filter()`s; `merge_silver` -> Delta/Iceberg `MERGE INTO`; `courier_payouts`/`restaurant_fees` -> `groupBy().agg()`. **Not changing:** the DAG structure (extract -> transform -> gate -> publish -> watermark), the Variables, retries and the branch. Airflow would call `SparkSubmitOperator` instead of a `PythonOperator`.

**8. Two consumers in one group.** Kafka splits the 4 partitions (3 of `order.events` + 1 of `courier.locations`) between them, a **rebalance**; each partition is read by exactly one of them. With 4 consumers each gets one partition. A 5th would be **idle**. The **number of partitions** is the maximum useful parallelism per topic. Note that `SeenEvents` is per process; that is fine because one `order_id` always goes to the same partition (key = order_id), so the same consumer.

**9. Reading the production primary.** The primary serves every app read and write. An hourly batch query (and on a big collection without an index on `updated_at`, a full scan) competes with the app for CPU, RAM and cache, so the app gets slower exactly during the busy hour. Real options: (a) read from a **dedicated analytics secondary** - a hidden replica-set member the app never uses - with `readPreference=secondary`; (b) **CDC** with Change Streams + the Kafka Connector, so the pipeline never queries the database and also sees deletes and every intermediate update (questions 1 and 2); (c) read a **nightly snapshot/backup** instead of the live DB. Whatever you choose, agree it with the app team and index the field you filter on.
